## Baseline

The portfolio began as a static vanilla JavaScript single-page application with five simulated operations demos and browser-local persistence. For this backend cycle, the clean starting point was `development` at `128cae13f8563dc5407d7ca24c75a87d3e07a878`: it already had a loopback Python standard-library JSON API, a SQLite current-state snapshot, compare-and-swap revisions, browser-cache fallback, and a backup command that ran SQLite `quick_check`. An isolated copy of that commit passed 16 Node tests, 15 Python API/preview tests, and `npm run check`. It did not retain server-side revision history or expose a restore endpoint; the backup check did not validate casebook/history consistency or wait until verification to publish the destination. This cycle preserves the working architecture and extends recovery and storage verification.

## Backend history cycle

- Added a SQLite history table that records each accepted snapshot and UTC timestamp in the same transaction as the active revision. A failed history insert rolls the active write back.
- Restore requests are limited to 4 KiB, since they contain only the expected head and source revision. Casebook updates keep their separate 1 MB cap.
- Existing casebook databases are upgraded in place by seeding their current snapshot into the new history table. The newest 25 snapshots are retained; older ones return 404 and cannot be restored.
- `GET /api/history` lists revision summaries (record counts and restore source); `GET /api/history/{revision}` returns a retained snapshot; `POST /api/restore` restores a retained snapshot only when the caller supplies the current revision. Restore creates a new head revision and records its source instead of decrementing the sequence.
- Schema version 2 is recorded in SQLite `user_version`. The migration seeds the prior current snapshot without resetting it; startup refuses a database marked with a newer schema.
- A schema-v1 migration test verifies the existing revision remains readable and the migrated store accepts the next consecutive revision.
- Each casebook API operation rechecks `user_version` and fails with HTTP 503 on a runtime schema mismatch, not only when the server starts.
- Retained history rows must be consecutive as well as strictly ordered; deleting a middle revision now fails closed across reads, health, writes, restore, and backup verification. A regression test confirms that a missing revision cannot be silently skipped.
- Static and JSON responses set a same-origin Content Security Policy plus `nosniff`, `DENY` framing, and no-referrer headers. API tests assert these headers on both HTML and JSON responses; the browser pass checks the policy does not block app scripts, styles, or same-origin state requests.
- Local requests with a Host value outside `localhost` and `127.0.0.1` are rejected with HTTP 421. This narrows DNS-rebinding exposure while keeping the documented browser and SSH-tunnel hostnames usable; it does not add authentication or make public exposure safe.
- Transfer-Encoding, duplicate Host/`Content-Length`/`Content-Type` headers, and GET/HEAD bodies are rejected. Early rejections close the connection before unread request-body bytes can be processed as a subsequent request; raw-socket checks exercised unsupported media type, unexpected/duplicate Host, duplicate length and content type, transfer-encoding, and GET-with-body cases.
- History reads, health checks, writes and restore validate all retained revision timestamps, lineage and casebook payloads. The full snapshot must also serialize as finite UTF-8 JSON, including extension fields, and integer values must remain exact in JavaScript; the active snapshot must match the newest history record. Corrupt or non-UTC timestamps, invalid lineage, non-portable extension values, or corrupt snapshots return HTTP 503 as server-side storage failures. A failed write or restore history insert leaves the previous active snapshot and history intact.
- Health output includes schema version and retained-history count. Active-state reads and health checks reject snapshots that fail domain validation or do not match their current history row; reads, health checks, writes and restores also fail closed if any retained history record is invalid. Python API tests verified normal restore, stale restore conflict, competing restore/write CAS, missing/expired revision rejection, migration from a pre-history SQLite schema, 25-revision pruning, history preservation in a SQLite backup, rejection of a logically mismatched backup head, unencodable input rejection, persistence of restore lineage across restart, and atomicity when either the write or restore history insert fails.

## Scope limits

The browser checks support the specific UI and workflow behaviors listed above. They are not a complete accessibility audit, cross-browser matrix, production acceptance, or operational suitability review. Automated checks ran with Node.js 24.19.0, Python 3.12.14, Playwright 1.62.0, and Chromium 154; the documented minimum Node.js and Python versions were not separately matrix-tested. The applications use synthetic, rule-based examples and a local SQLite snapshot with a browser-cache fallback. They do not connect to infrastructure, scan for vulnerabilities, probe networks, send notifications, enforce identities, or provide cloud persistence. The preview server binds only to loopback; use an SSH tunnel for a private VPS demo. No CI pipeline or public deployment was configured.
